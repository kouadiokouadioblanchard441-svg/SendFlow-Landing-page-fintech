---
name: Telegram monitoring and IP blocks
description: SendFlow's user-requested Telegram security alerts and Node-level IP blocking constraints.
---

For SendFlow, monitoring is off until both the bot token and private-group chat ID are configured in Plesk's Node environment. The user wants no extra Telegram-specific settings there. Derive the webhook secret server-side from the bot token, and authorize commands/IP-block callbacks by checking the sender's current creator/administrator role in the configured group through Telegram's API. The bot must be a group administrator. Never put the bot token or derived webhook secret in source, Git, browser variables, or frontend responses.

The user explicitly requires the bot to operate only inside the configured group: silently ignore private-chat commands and callbacks, and only accept group/supergroup messages whose chat ID matches the configured group. Do not send a private-chat denial message.

The user authorized request metadata logging for all requests reaching Node/Express, 90-day retention, and local GeoIP databases so visitor IPs are not sent to a live lookup API. Plesk or a CDN may serve assets before Node; don't claim those requests are captured. City/country are approximate; ASN/ISP and connection type are database estimates, not guaranteed exact mobile carrier or 3G/4G/5G. Do not trust forwarded client IP headers unless exact proxy addresses have been verified and configured; never trust all proxies. If Node only sees a private Passenger address, don't treat it as a visitor IP or offer an IP block action. Don't store request bodies, query strings, cookies, or authorization headers. When IP blocking is enabled, failure of the persistent block store must fail closed with a service-unavailable response; never silently pass requests when the block list cannot be checked.

Visit notifications should include the server-observed public IP when the trusted-proxy chain provides one, local approximate GeoIP, and browser/OS/device categories inferred from the request User-Agent. Never persist or display the raw User-Agent; treat these labels as client-declared estimates. A "new IP" means first appearance in the retained 90-day site-visitor history, not a new IP for an account; the public landing has no authenticated visitor account to correlate.

**Why:** The user requested Telegram alerts, visitor/request commands, and IP block/unblock controls; wants only the bot token and group ID as Telegram-specific Plesk settings; chose Telegram group administrators as the action allowlist; requires that private chats receive no bot responses; wants local rather than live external GeoIP lookup; and requested detailed visit notifications. Misidentifying Passenger's proxy IP could block every visitor; silently passing traffic when the persistent deny list is unavailable would make configured bans ineffective.

**How to apply:** Keep the integration off until both Telegram values are configured; explain request/IP/approximate-location and estimated client metadata collection and 90-day retention in the published privacy policy before activation; restrict group membership; make the bot an administrator; install and maintain licensed local City, ASN, ISP, and connection-type MMDB files under PLESK_MEDIA_DIR; verify proxy behavior on Plesk before relying on visitor IPs; and return 503 rather than bypassing the block check when persistent storage is unavailable.
